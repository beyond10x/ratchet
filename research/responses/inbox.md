## C. What went wrong
C1: The test step grew to its 120 s bound without a commit that slowed any case. **seen** 2026-11-23: 56 s with 894 cases, 118 s with 913, then one run ended at 120 s with 928 cases at a host load average of 82 to 112; that run turned the release gate red. Noticed only when the bound was hit (**inferred**: the growth came with the 37 cases of the 2 stories before it). Measured afterwards: the run was bound by waits, not CPU (26.6 s of CPU over 87.6 s; 408 s of summed case time), and one fixture was made per case (5 process starts each). A check on the summed case time against the last accepted value, or on "process starts per case", would have shown it with the first of those stories.
C2: The same 120 s bound, red on a correct tree when the shared host is loaded (**seen**: 2 runs on 2026-11-23, 118 s at a load average of 55 to 104 and one ended at 120 s at 82 to 112, on 20 CPUs; the same tree took 68 s at 68 to 75). Wall time on a shared host measures the host as much as the change.
C3: None loosened in this repository: the folder's rule forbids raising a timeout, adding shards or waiting longer as a fix (**seen** in the rules file), and the 2 budget defects were fixed in the cases. One acceptance line of a story was changed after measurement (CPU time minus 30 % became case time minus 40 %), recorded with its options in the story.

## E. Quality in plain words
E1: Every message that was accepted is delivered once and never marked delivered when nobody received it. The service does what its specification says, and the specification, the generated code and the documents never disagree. A failure says in one line what failed and exits with a status a script can rely on. The gate answers in a few minutes and a red means the change is wrong, not the machine. What the product cannot do yet is written down where a user looks first.
E2: Today: specification against implementation (conformance), generated files in sync, exit statuses and lines (cases). With work: "never marked delivered without a reader" for every path (mutants in the gate, per changed file); "a red means the change is wrong" (measure CPU time or case time against a baseline, not wall time on a shared host). Never by machine alone: whether the limits page names what a user would trip over.
E3: End users: a message shown twice, or marked delivered that nobody saw. Developers and coding agents: a gate that takes longer than last week or goes red on an unchanged tree. Operators: a command that changes a file it could not read, or an exit status that changed meaning. API consumers: a response shape that differs from the published OpenAPI document.
E4: The summed case time of the test step (and its CPU time), measured in the gate, may not exceed the value accepted on `main` by more than 10 %; an increase is accepted only by a commit that changes the stored value and says why.
